# 看图看不全，瓶颈在预算方向，不在模型

2026-08-24 DeepSeek Harness 发版，多模态模型 `DeepSeek-V4-Flash-Vision-Exp`
同日在 API 平台上线。问题随即提出来：分身看图这一段能不能换成它。

问题背后有个没说出口的前提——**看图看不全是因为模型不够强**。历史数据看着
也支持这个前提：175 次成功的图片理解里有 66 次被截断（37.7%），另有 35 条
`ANSWER_BUDGET_EXHAUSTED`（预算耗尽时一个字都没答出来）。

**这个前提是错的。** 实测之后决定：**不换模型，改预算方向。**

## 事实：换模型几乎没有差别

拿群里真实收到的 12 张图，两边各跑一次。基线是线上现役配置
（`kimi-k2.6`，不思考，1024 token）；候选是 DeepSeek 的目标配置
（`deepseek-v4-flash-vision-exp`，开思考，4096 token）。

| | 现状 Kimi | 候选 DS |
|---|---|---|
| 成功 | 12/12 | 12/12 |
| 截断 | 1 | 1 |
| 均耗时 | 15.5s | 14.5s |
| 均字数 | 1148 | 995 |
| 硬 token 覆盖 | 8 张打平，各赢 2 张 | |
| 编造 | 无 | 无 |

两个决胜局，一边一个：

- **20 行 × 14 列的调拨单截图**：Kimi 6/11，DS 10/11。Kimi 不是认错，是**整列
  跳过物料编码**——19 个编码一个都没念出来。
- **两处红框的数据库查询截图**：Kimi 7/7，DS 3/7。DS 跑满 34 秒、吃光 4096
  token 仍然截断，好几个关键字段全没说出来。

红框两边都认得出来，被人用红框圈出来的那个金额两边都抓到了。

## 事实：真正的病因是两个预算的方向反了

看图有两个预算：`vision_max_tokens`（模型这一次最多能说多少）和
`vision_max_chars`（多长的描述才让它进对话上下文）。

改动前的默认值是 1024 配 2000。实测换算率是 **1 token ≈ 1.7 个中文字**
（kimi-k2.6 在 1024 上限下吐出 1750 字后 `finish_reason='length'`）。也就是说
1024 token 只够吐 1750 字，**永远够不着 2000 字那道墙**。

后果不是「少了 250 字」，是**每一次截断都发生在错误的一端**：

| 截断发生在 | 可预测吗 | 模型知道吗 | 最坏情况 |
|---|---|---|---|
| 代码这一端（`max_chars`） | 是 | 是，必带 `truncated` | 少最后一截 |
| 模型那一端（`max_tokens`） | 否 | 否 | 一个字都不剩 |

那 35 条 `ANSWER_BUDGET_EXHAUSTED` 就是最坏情况真的发生了。66 次截断则是
它温和一些的形态。两者同源，源头是这个方向。

作参照，同样抢一个上下文窗口的 `attachment_max_chars` 是 **30000**。图片这一侧
配 2000，是附件的 1/15——保守到了产生故障的程度。

## 决策

1. **`vision_max_tokens` 换算后必须大于 `vision_max_chars`。** 这是硬约束，
   加载配置时当场 `ConfigError`，不是警告。配反了不会报错、只会让描述
   悄悄缺一截——看图模块里早就记着同一条教训：静默无效的参数比报错的参数
   危险得多。
2. 默认值改为 **4096 / 6000**，两处同时改，配置测试的断言盯着不走散。
3. ~~**看图继续用 `kimi-k2.6`。** 换 DeepSeek 见下。~~ **已被后续决策取代**
   （2026-09-10）：V4.1 Flash 原生多模态，看图与对话并到同一个模型；下面那条
   「否决换 DeepSeek」的理由随之失效，Moonshot 账户当时也已欠费停用。
4. **`vision_thinking_enabled` 保持关闭。** 这条纪律此前记成 Kimi 的脾气，
   实测证明它是这条链路的通则：DeepSeek 开着思考照样会不可预测地吃光预算
   （那张 34 秒仍截断的红框截图）。换供应商不解除它。

## 被否决的选项

**换成 `deepseek-v4-flash-vision-exp`。** 接得上，而且接起来几乎没有成本：
它就在 `api.deepseek.com` 上，分身的对话模型已经在同一个
域名、用同一把密钥、走同一个请求函数；看图模块是 OpenAI 兼容形状，
**一行代码都不用改**，改三个环境变量即可。顺带还能少管一把 Moonshot 的密钥。

否决理由就是上表：12 张真图打不出差别。为一个测不出收益的改动去动一条刚
稳定下来的链路（8-19 之后 51 张图零失败），不划算。

**不需要 DeepSeek Harness。** 推文说的是 harness 新增了这个模型选项，但
harness 是个 CLI，它调的就是那个公开 API。分身要的是识图能力，不是一个
agent 外壳——那是排查 agent 那个位置的事，与本决策无关。

**只放大 `max_chars`、不动 `max_tokens`。** 那会把方向反得更厉害。

## 什么条件下推翻它

DS 唯一的显著优势在**超密集业务表格**（多行多列的调拨单、对账表）。今天 12 张
样本里只有 1 张是那个形态，所以不够。**如果分身要读的图开始以那类表格为主，
重测。** 重测就重测，别照抄本文的结论——两边模型都在动。

重测时注意一件容易搞混的事：关着思考的 DS 会**主动概括**而不是逐行罗列
（它会写「模式为 `SHFBDC414xxx`，从 414204 到 414220」）。那不是漏认，
按「提到了几个编号」去数会把它冤枉成幻觉。

## 后果

- 历史上那 66 次截断不会追溯重看——媒体理解读过一次就不再读，
  重放不该重新花钱（既有纪律）。
- 本次实测只覆盖 12 张图、每边一次，不足以支撑更强的结论。它足够回答
  「要不要换」，不足以回答「哪家更强」。

## 没有一并解决的

**98% 的看图调用是白花的。** 同日查到：269 条群图片事件里，最终被挂进
封口清单、真正进了模型上下文的只有 **5 条**。其余 264 张图都是一进群就付钱
看一遍，然后再没有任何一次回答用到它。

那是「什么时候看」的问题，本决策只管「看的时候能不能看全」。两件事独立，
另行处理。
