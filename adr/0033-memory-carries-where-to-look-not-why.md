# 排查记忆记「改哪里」，不记根因，每次重新确认

证据闭合之后，数据库变更平台（Archery）能给出的事实相当厚：动作、目标表与字段、
定位键、执行时间、影响行数、前置值（回滚 SQL）、处置人。问题是这些事实该以什么形状
沉淀成可复用的排查记忆。

实查当天下午的两张工单足以说明诱惑在哪：

```
17:46  update <回传消息表> set success = 0 where <定位键> in (…九行…)
18:04  update <回传消息表> set message = '{…单位编码…}' where <定位键> = 其中一行
```

从这两条能推出一个相当合理的故事——单位编码错了导致回传失败，研发先重置状态
想重推，没成，二十二分钟后改掉编码再推。**先重置后改值的时间顺序还额外支持它。**
但研发没在群里说过，工单里也没写。这个故事是推的，不是查证的。

决定是：**排查记忆记「这类症状该往哪儿动」，不记「上次为什么」；
它进入下一次排查时的身份是待验证的假设，不是结论。**

## 记忆缩短排查，不替代排查

这条是本 ADR 的中心，其余都是它的推论。

分身带着记忆进入一次新排查，记忆的作用是把搜索空间从「整个系统」收窄到
「先看这张表这个字段、按这个键把行捞出来」。**收窄之后仍然要查。**
记忆不产出结论，只产出更快到达结论的路径。

因此记忆里存的是：目标表与字段、定位键、适用条件、**这次要重新跑一遍的复验查询**、
已知反例。不存：根因叙述、上次的具体取值、历史 SQL 的可执行原文。

## 为什么根因不进记忆

不是因为推断容易错——推断错了下次查一遍就纠正了。

是因为**标记会被磨平**。排查记忆要被注入下一轮上下文，一条标着「推断」的根因，
在下游读它的 agent 眼里，跟事实的差别只剩一个形容词，而那个形容词经不起
两三轮转述与摘要。一旦磨平，它就从「缩短排查」变成「跳过排查」，
恰好是本 ADR 要防的那件事。

根因假设有它该待的地方：**影子诊断**（ADR-0022）。它「只写本地，
不进群、不进群记忆、不构成排查任务的结论」，它的对错「由那件事最后
实际怎么被处理来判定」。假设留在那里能被后来的事实检验；搬进记忆就检验不了了。

**修复性质同样不自动判定。** 一次性修数、临时绕过、永久修复的配套动作，
SQL 一律看不出来。`set success = 0` 可能是把九条卡住的回传重推一遍，
也可能是推送逻辑本身坏了、这只是手工重触发。不猜。

## 与只读边界的关系

「分身知道该改哪里」不等于分身去改。当时的边界是分身只读：不碰写路径，
不提交工单，不生成修数草稿。记忆支撑的是**说得出该往哪儿动**，执行始终是人。

本 ADR 定的是记忆的形状，不是提前开放「说出该改哪里」那个更后面的阶段。

## 被否决的选项

**记根因，但打上「推断」标记。** 保留了那个故事，下次可能省半小时。
否决理由见上：标记在多轮注入里活不下来，而它一旦失效，代价是把人往
错方向带半小时，且没有任何机制会提示这条根因从未被证实。

**只记「上次研发动了哪张表哪个字段」这条历史事实。** 这是本轮最初的提法，
被使用者否掉：他要的不是查得到上次干了什么，而是**分身自己判断得出这次
该往哪儿动**。历史事实是一条记录，方法才是可复用的资产——差别在于
前者只对同一张单据有效，后者对同一类症状有效。

## 已知没有解决的

**「排查确认」的通过条件没定。** 分身拿着记忆说「先看 `message` 里那个字段」，
它要重新观察到什么，才够格把假设升级成这次的结论？哪些生产观察只支持假设、
哪些足以支撑一条结论，本 ADR 不回答。

**适用条件怎么写、谁判定这次适用，没定。** 问题簇的强事实锚点规则（相同稳定
错误码或报错原文、相同「业务对象 + 操作 + 症状」）是候选答案，但记忆的适用条件
未必与聚类条件同形——聚类判的是「这两个问题是不是同一类」，适用判的是
「这条方法能不能用在这个问题上」。
