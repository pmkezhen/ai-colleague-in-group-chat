# 对话模型充当大脑，Codex 是它的一个工具

原设计让本仓库的代码判断每次表达属于闲聊、发起排查、补充证据、进度还是停止，并为此建立了意图分类器、置信阈值策略和评测基准；Codex 只在判断完成后被当作执行器调用。现改为：目标消息先交给对话模型，由它自行决定能直接回答（闲聊）还是需要调用「Codex 排查」这个工具，其余四类意图相应变成它可以调用的工具。做出这一改变是因为对话模型本来就具备工具选择能力，用规则和阈值复刻这项能力等于在一个会思考的部件之外再造一个更弱的判断层。

代价是分流判断不再可离线评测，判错时的修正手段从改代码变成改提示词；换来的是意图分类器、阈值策略、`IntentThresholdPolicy` 的三方批准流程与整套意图评测（约 1300 行代码与测试）全部不再需要。

安全边界因此必须移到工具调用那一刻而不是留在模型内部：生产资源准入、凭证输出拦截和外发限速防的正是「模型出错或被诱导」，逻辑上不能由模型自己把守。

本决策取代早先「闲聊与排查各用一个隔离的 Codex 会话」的措辞——隔离本身保留，但闲聊侧现在由对话模型承担，不再是一个 Codex 会话。

## 转发，而不是编排

对话模型的职责到「这是不是闲聊」为止。判定不是闲聊时，**把原问题转给排查工具，由它全权处理，结果直接反馈回群**；对话模型不拆解问题、不规划查询步骤、不多轮调度工具。

这样划分是因为排查工具本身就是个能自己规划的 agent，让对话模型在它之上再编排一层，等于把同一件事做两遍，且两边对「该查什么」的判断可能打架。代价是回复的语气由排查工具决定，闲聊与排查两条路径的措辞风格会有差异。
