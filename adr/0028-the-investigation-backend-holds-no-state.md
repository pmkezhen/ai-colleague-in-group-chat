# 排查后端不持有状态，记忆与轨迹全部归分身

早先一条决策（ADR-0021，未收录）把排查工具定义成「外部编码 agent 的 headless
子进程」，决定性的理由写的是「工作目录决定它是谁」——在人格主号平时排查用的
项目目录里起一个 agent，十余条排查记忆、一批 skill、配好的 MCP「靠一个 `cwd`
全部接上」。

**这个论证不成立，而且它正在把项目锁死在一个具体 CLI 上。** 决定是：
**排查后端不持有任何状态**。记忆、处置轨迹、影子诊断、任务、材料一律由分身
持有，起排查时作为上下文显式注入。后端只是一次无状态调用。

## 事实：那些资产不在工作目录里

实查 2026-08-15：

```
$ find <那个项目目录> -iname "*memor*"
（无输出）
```

那 14 条记忆在 `~/.claude/projects/<路径 slug>/memory/`，共 43 KB。
Claude Code 拿工作目录的路径算了个 slug，在**自己家里**建了个目录存的。
工作目录里没有任何文件指向它。

三家后端各存各的，谁也读不到谁：Claude Code 在 `~/.claude/projects/<slug>/memory/`，
Codex 在 `~/.codex/memories/` 加一个 sqlite（1.7 MB），dsh 在 `~/.dsh/`。
换后端不是「接不上」，是**丢**。

已经在用的那个业务域就是活反例。ADR-0021 白纸黑字写着「不绑定具体 CLI」，但那
14 条记忆没有一条是谁决定要存在 Claude Code 库里的——它们是自动落进去的。
**锁定不是因为没人守规矩，是因为默认行为自己完成了锁定，而没人察觉。**

因此本 ADR 的第一句是原则，第二句是这个阶段兑现它的具体动作。原则长期有效，
动作随阶段可换。

## 原则：状态归分身，算力归后端

凡是造在后端私有库里的东西，换后端就丢；凡是不想丢的，都必须由分身持有。

推论是后端应当**无状态**：给它任务和上下文，它用工具查，返回结论，
**它什么都不留下**。ADR-0021 想要的「可替换」，靠「让后端继承」永远做不到，
只有靠「不让后端持有」才做得到。

这条不是好看的原则，是队列设计本身就要求的。排查队列的状态机规定
`RUNNING → WAITING_EVIDENCE → QUEUED → RUNNING`：任务要追问就
必须离开运行通道（全局单通道由任务表上的部分唯一索引兜底），
补证后重新排队再跑。任务离开 RUNNING 又回来，中间那段历史只能由分身记着——
后端持有状态在这里根本行不通。

## 这个阶段的动作

1. **冷启动的工作目录里必须放一份 `AGENTS.md`**，规定排查结论写进仓库内目录，
   不要只留在会话记忆里。三家后端都读 `AGENTS.md`（dsh 的 `.agents/skills` 是
   rank 200 的发现根，已实测）。这一步执行完就固化在文件系统里，
   之后不依赖任何人记得。
2. **接缝一次性返回**：`InvestigationRunner` 传任务与上下文，返回结论。
   另留一个可选的进度回调。
3. **回调只喂本地**：中间过程写进处置轨迹与离线蒸馏语料，**永不进群**。
   它的价值不是给人看进度，是把「查了什么、看到什么」存下来——那正是
   既有工单和聊天记录都没有的那一段，也是影子模式（ADR-0022）蒸馏的基本单元。
4. **群里的进度是拉取式**：被 `@` 问了才答，由对话模型读本地记录后汇总，
   像真人那样说「正在查，东西有点多，稍等」。出口仍是已有的那一个，
   凭证输出拦截与「群内排查结论」的规则原样生效，不新建裁剪层。
5. **重排队后注入完整处置轨迹**，不注入摘要——排查的细节往往就是根因。
6. 工作目录取新业务域的项目目录。第一阶段不碰代码
   （日志平台与代码仓库的只读权限本次不申请），等权限批下来再放代码进去。

后端选谁**本 ADR 不指定**，接缝先建。哪家排查更准没有任何实测支撑，
而影子诊断本来就是用来测准确率的——现在凭感觉选，
等于把该用数据回答的问题提前用直觉答了。

## 被否决的选项

**让后端持有记忆，承认绑定某一家。** 省掉整套写入与注入机制，冷启动当天就能开工。
否决理由是这恰好是老业务域今天的处境：想换后端得先迁记忆，而迁移的成本在
需要换的那一刻才会显现。

**把记忆放进新项目目录，让三家靠 cwd 都读到。** 形状最干净，
`.agents/skills` 是三家共识的约定。否决理由是它依赖代码仓库的只读权限
先批下来、代码先检出——而那正是当前唯一的阻塞项。等权限到位后，
它可以作为动作 1 的升级形态。

**要求后端流式吐进度、直接发群里。** 否决理由是每条中间输出都是一次外发，
而中间输出恰恰全是「群内排查结论」明令不得入群的东西：整份日志、
整批查询结果、无关记录。拉取式汇总只有一次敞口，内容形态还与普通回复相同。

## 已知没有解决的

**「工作目录锁定」只挡写，不挡读。** dsh 的凭据文档自己写明：工具进程以同一
用户身份运行，文件策略限制的是修改而非读取，「也没有任何沙箱模式会把它单独
挑出来」。也就是说排查子进程能读这个用户可读的任何文件，`.env.local` 在内。
这跟选哪个后端无关，是同一用户身份起子进程的通病。「工作目录锁定」这个说法，
实际保护力比字面弱。真正的隔离要靠单独的 OS 用户或容器，本 ADR 不解决。

**新业务域记忆的写入与注入机制尚未建。** 动作 1 只保证结论落在仓库内目录，
没有规定分身怎么把它们读回来、怎么注入。这是明账欠账，靠本 ADR 记着，
没有别的担保。
